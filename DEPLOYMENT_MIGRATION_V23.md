# Развёртывание v23 — Google Apps Script + Google Sheets

## Перед обновлением

1. Сделайте копию рабочей Google Spreadsheet.
2. Экспортируйте резервную копию листов `Настройки`, `Задачи`, `Касса`, `Расходы`, `Инциденты`/`Поломки`, `Сотрудники`, `Информирование`, `ДельтаСинхр`.
3. Сохраните текущую версию deployment Apps Script и URL `/exec` для отката.
4. Убедитесь, что у владельца Apps Script есть доступ к таблице и Google Drive.
5. Не очищайте `API_OPERATIONS`, `ДельтаСинхр` и бизнес-листы при обновлении.

## Развёртывание

1. Замените исходник Apps Script на `Code.gs`.
2. Проверьте, что Apps Script запрашивает необходимые разрешения: Google Sheets, Google Drive, UrlFetch (Telegram).
3. Создайте новую версию Web App deployment. Проверьте доступ по правилам вашей организации.
4. Опубликуйте все файлы фронтенда из одного архива. Не смешивайте HTML старой версии с JS v23.
5. Проверьте `config.js`: `COFFEE.API_URL` должен указывать на актуальный `/exec`.
6. Откройте приложение в приватном окне и войдите как владелец. Проверьте, что вход подтверждается сервером.
7. Войдите под тестовым бариста. Убедитесь, что UI подтверждает профиль сервером, а не только локально.
8. Проверьте отправку чек-листа, кассы, подтверждения объявления и инцидента. В каждом случае имя сотрудника в таблице должно соответствовать имени серверной сессии.
9. Попробуйте отправить эти же операции без `sessionToken`: сервер должен вернуть `STAFF_SESSION_REQUIRED`.
10. Проверьте отрицательные суммы, дату `2026-02-31`, повтор одного `operationId` и пакет кассы из 32 дней — сервер должен отклонить некорректные запросы.
11. Загрузите тестовое фото. Проверьте появление файла в папке `Кофейня — Медиаархив Смен` и записи в листе `Медиафайлы`.
12. Проверьте GET для Dashboard, Report и Admin: запрос должен работать с `sessionToken`, без передачи PIN в URL.
13. Проверьте offline: локальные записи помечаются pending и остаются в очереди до серверного подтверждения. После возврата сети войдите повторно и проверьте повторную отправку.
14. Проверьте второй браузер/устройство и убедитесь, что данные не дублируются.

## Первичная настройка PIN

До production обязательно выполните `setup_initial_credentials` из админской сессии:

- задайте новый PIN владельца;
- задайте отдельный PIN каждому активному сотруднику;
- проверьте вход новыми PIN;
- проверьте отказ старых заводских PIN.

После установки `FACTORY_PINS_DISABLED=1` отсутствующие индивидуальные PIN больше не подменяются заводскими значениями. Если часть сотрудников не получила PIN, они не смогут войти — это ожидаемое безопасное поведение.

## Откат

Если критический сценарий не работает, верните предыдущую версию Apps Script deployment и предыдущий комплект фронтенда. Не удаляйте новые технические листы и журналы. Перед повторной попыткой проверьте серверные логи и таблицу на частично выполненные операции.
