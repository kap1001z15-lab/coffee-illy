# Карта бизнес-логики и расчётов (`BUSINESS_LOGIC_MAP.md`)

**Актуальный статус релиза:** `v78` (полная обратная совместимость с расчётным ядром `v78`)  
**Назначение документа:** Фиксация всех действующих алгоритмов, математических формул, правил валидации и контрольных эталонных значений, которые не подлежат изменению при редизайне интерфейса.

## 1. Расчёт счётчиков кофемашины и перехода через `999 → 0`

Модуль реализации: `js/sales-reconciliation.js` (`counterDelta`) и `js/analytics.js` (`window.coffeeCounterDelta`).

### 1.1. Правило расчёта

Механический/электронный счётчик порций кофемашины работает в трёхзначном диапазоне `0..999` (модуль `MOD = 1000`). При достижении `999` следующее срабатывание переводит счётчик в `0`.

- Если `prev` и `cur` находятся в диапазоне `0..999`:
  - при `cur >= prev`: `delta = cur - prev`;
  - при `cur < prev` (переход через предел `999 → 0`): `delta = (1000 - prev) + cur`.
- Если значения превышают `999` (расширенный счётчик):
  - при `cur >= prev`: `delta = cur - prev`;
  - при `cur < prev`: возвращается `null` (требуется ручная проверка).

### 1.2. Автоподстановка начального счётчика смены

В терминале бариста (`js/page-terminal.js`, `getActiveCounterInfo`) поле начального счётчика `counterStartIn` автоматически предзаполняется конечным значением `counterEnd` предыдущей зафиксированной смены. Благодаря этому в сценарии **«Сдать смену»** сотруднику достаточно ввести только одно число — показание счётчика на конец смены (`#quickCounterIn`).

### 1.3. Контрольные эталонные значения (проверяются автотестами)

| Сценарий | Начало (`prev`) | Конец (`cur`) | Эталонный результат (`delta`) |
| :--- | :---: | :---: | :---: |
| Обычная смена | `735` | `777` | **`42`** |
| Переход через предел 999 (тест 1) | `998` | `2` | **`4`** |
| Переход через предел 999 (тест 2) | `999` | `0` | **`1`** |
| Смена Алины (эталон 04.11.2026) | `648` | `735` | **`87`** |

## 2. Сверка продаж (CSV), кофемолки и списаний

Модуль реализации: `js/sales-reconciliation.js` (`CoffeeSalesReconciliation.reconcileGrinderAndSales`).

### 2.1. Классификация номенклатуры

Каждая строка из отчёта `Продажи.csv` классифицируется функцией `classifyCoffee(itemName)` с учётом пользовательских правил (`db.nomenclatureRules` / лист `Настройки`):

1. **Исключения (добавки и модификаторы):** позиции, совпадающие с `ADDON` (`молоко`, `сироп`, `мёд`, `маршмеллоу`, `топпинг`, `открытка`, `десерт от бариста`), не учитываются как отдельные напитки в топе продаж и не расходуют порции зерна.
2. **`coffee` (кофейные напитки на зерне):** эспрессо, американо, капучино, латте, раф, флэт уайт, макиато, глясе, моккачино, бамбл, эспрессо-тоник, айс-латте, фильтр-кофе, доппио, лунго, ристретто, кофейные напитки `ILLY`.
3. **`non_coffee` (некофейные позиции):** чай, какао, горячий шоколад, лимонад, милкшейк, смузи, фреш, вода, сок, матча, глинтвейн, выпечка, десерты, сэндвичи, круассаны, макаронс, сиропы, стаканы.
4. **`review` (требует ручной классификации):** любая новая позиция меню, не попавшая в словари `coffee` / `non_coffee` и не имеющая сохранённого правила в `db.nomenclatureRules`.

### 2.2. Формулы сверки счётчика и продаж

Для каждой смены или операционного дня рассчитываются:

- `grinderShots = counterDelta(counterStart, counterEnd)` — фактическое число помолов по счётчику;
- `soldCoffee` — сумма `qty` всех проданных позиций класса `coffee`;
- `writeoffShots` — количество документированных технических списаний кофе в порциях (настройка помола, пролив);
- `accountedShots = soldCoffee + writeoffShots` — объяснённое количество срабатываний счётчика;
- `diff = grinderShots - accountedShots` — расхождение счётчика;
- `unaccountedShots = Math.max(0, diff)` — необъяснённые срабатывания сверх кассы и списаний;
- `overAccountedShots = Math.max(0, -diff)` — превышение кассовых продаж над счётчиком.

Статус сверки (`status`):
- `'ok'` — `unaccountedShots === 0`, `overAccountedShots === 0` и `reviewQty === 0`;
- `'warning'` — есть позиции на проверку (`reviewQty > 0`) или расхождение счётчика (`diff !== 0`).

### 2.3. Контрольный эталон сверки (`sales-alina-2026-11-04.csv`)

При входных параметрах `counterStart = 648`, `counterEnd = 735`, `writeoffShots = 1` на файле `tests/fixtures/sales-alina-2026-11-04.csv` система обязана выдавать строго следующий результат:

| Показатель | Поле JSON | Эталонное значение |
| :--- | :--- | :---: |
| Выручка по файлу продаж | `revenue` | **`1687`** руб. |
| Продано кофе (порций) | `coffeeQty` / `soldCoffee` | **`52`** шт. |
| Продано некофейных позиций | `nonCoffeeQty` | **`41`** шт. |
| Позиций, требующих ручной классификации | `reviewQty` | **`5`** шт. |
| Срабатываний счётчика (`735 - 648`) | `grinderShots` | **`87`** шт. |
| Списания кофе в порциях | `writeoffShots` | **`1`** шт. |
| Учтённые порции (`52 + 1`) | `accountedShots` | **`53`** шт. |
| Необъяснённая разница (`87 - 53`) | `unaccountedShots` (`diff`) | **`34`** шт. |
| Статус сверки | `status` | **`warning`** |

## 3. Правила расчёта кассы, слияния смен и корректировок

Модули реализации: `js/page-terminal.js`, `js/sync.js` (`applyLocalMutation`), `Code.gs` (`submitCash_`, `batchSubmitCash_`).

### 3.1. Два режима записи кассового дня (`mergeMode`)

1. **`mergeMode: 'sum'` (по умолчанию для `submit_cash` из терминала бариста):**
   - Используется, когда в один день работают два бариста (утренняя и вечерняя смены, например Алина и Соня).
   - Если вторая смена передаёт агрегированный дневной CSV-файл, включающий транзакции первой смены, система распознаёт пересечение по `csvHashes` / `shiftsMap` и не удваивает выручку.
   - Если передаются отдельные смены двух разных бариста, их выручка (`cash`, `card`, `checks`, `writeoff`, `writeoffShots`) суммируется в дневную сводку, имена объединяются через `, ` (`Алина, Соня`), `counterStart` берётся как минимум начала дня, `counterEnd` — как максимум конца дня, а детальная разбивка по каждому сотруднику сохраняется в поле `shifts` (`Смены JSON`).
2. **`mergeMode: 'replace'` (по умолчанию для `admin_cash` из панели владельца):**
   - Используется при административной сверке с фискальным Z-отчётом.
   - **Запрет бесследной перезаписи:** при сохранении корректировки через `admin_cash` система обязана сохранить в истории записи (`correctionHistory` / `Смены JSON`) первоначальные значения бариста (`prevCash`, `prevCard`, `prevChecks`, `prevWriteoff`, `prevCounterStart`, `prevCounterEnd`), имя автора корректировки, время изменения и указанную причину расхождения (`diffReason`).

### 3.2. Защита от повторной загрузки одного и того же CSV

Каждому загруженному файлу `Продажи.csv` или `Транзакции.csv` вычисляется детерминированный отпечаток `csvHash(text)`. Хэши сохраняются в колонке `Хэши CSV` листа `Касса` и колонке `Хэш CSV` листа `Продажи`. Повторная загрузка файла с тем же хэшем за ту же дату блокируется на клиенте и на сервере.

## 4. Финансовая модель и расчёт прибыли (P&L)

Модуль реализации: `js/analytics.js` (`window.coffeeCalculateFinancialModel`).

### 4.1. Принцип честного расчёта прибыли

В соответствии с требованиями концепции и аудита **строго запрещено** подменять себестоимость или чистую прибыль условным фиксированным процентом (например, `35%` от выручки). Все показатели делятся на три прозрачных уровня:

1. **Фактические показатели (подтверждены документами):**
   - `revenue = sum(cash + card)` по сданным кассовым сменам за период;
   - `checksTotal = sum(checks)`;
   - `avgCheck = checksTotal > 0 ? Math.round(revenue / checksTotal) : 0`;
   - `wasteCost = sum(writeoff)` (прямые денежные списания);
   - `nonPayrollOpex = sum(expenses)` (внесённые операционные расходы кроме статьи «Зарплата»).
2. **Расчётные показатели (по действующим ТТК и ставкам):**
   - Себестоимость каждой проданной позиции рассчитывается по её техкарте из листа `Техкарты`:  
     `unitCost = costBeans + costMilk + costSyrup + costCup`;
   - Маржинальность позиции: `margin = price - unitCost`, `foodCostPct = Math.round((unitCost / price) * 100)`;
   - Если по смене загружена детальная номенклатура продаж (`products`), `COGS` считается точно по количеству проданных позиций и их ТТК; если детальный CSV за день ещё не загружен, используется средневзвешенный Food Cost % действующей матрицы ТТК с явной пометкой `≈ расчёт по ТТК`;
   - `grossProfit = revenue - cogs` (Валовая прибыль);
   - `effectivePayroll` — фактические выплаты по статье «Зарплата» либо расчётное начисление ФОТ за отработанные смены (`baseShiftRate + revenuePct`);
   - `netProfit = grossProfit - effectivePayroll - nonPayrollOpex - wasteCost` (Чистая прибыль).
3. **Плановые и прогнозные ориентиры:**
   - Дневные планы выручки, среднего чека и количества чеков по дням недели (`Пн–Вс`, лист `Планы`);
   - Прогноз выполнения месячного плана и точки безубыточности (`coffeeSmartEngine.simulate`).

## 5. Таймлайн чек-листов, окна доступа и «Красные флаги»

Модуль реализации: `js/analytics.js` (`coffeeGetBlockWindow`, `coffeeEnforceOverdueChecklists`, `coffeeEvaluateRedFlags`).

### 5.1. Шесть базовых блоков таймлайна

| ID блока | Название блока | Окно по умолчанию | Правило доступа в терминале |
| :--- | :--- | :---: | :--- |
| `blk_open` | `Открытие` | `07:30 – 08:30` | Доступен в пределах окна; после дедлайна блокируется со статусом `🔒 Закрыто (просрочено)` до разблокировки руководителем |
| `blk_lc1` | `Лайн Чек 1` | `08:30 – 09:30` | Проверка готовности бара и витрины после утреннего открытия |
| `blk_lc2` | `Лайн Чек 2` | `14:00 – 16:00` | Дневная проверка чистоты, остатков молока и заготовок перед вечерним пиком |

### 5.2. Автоматический детектор «Красных флагов» (`coffeeEvaluateRedFlags`)

Система автоматически формирует предупреждения для панели владельца в следующих случаях:
1. **Расхождение с Z-отчётом (`level: 'red'`):** разница между суммой смены бариста (`cash + card`) и фискальным Z-отчётом (`zTotal`) превышает `10 руб.`.
2. **Аномалия счётчика кофемолки (`level: 'red' / 'warn'`):** наличие необъяснённых срабатываний счётчика (`unaccountedShots > 0`) сверх проданного кофе и списаний в порциях.
3. **Превышение нормы списаний (`level: 'warn'`):** денежные списания за день превышают установленный норматив `WO_NORM` (`15 руб.`).
4. **Просрочка чек-листа (`level: 'red'`):** регламентное окно завершилось, а отчёт по блоку не сдан (автоматически создаётся системный инцидент просрочки и отправляется оповещение в Telegram).
